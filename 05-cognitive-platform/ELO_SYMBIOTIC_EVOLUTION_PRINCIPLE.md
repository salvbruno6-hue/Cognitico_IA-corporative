# ELO Symbiotic Evolution Principle

## Status

Canonical architectural principle proposed for governed admission.

## Definition

ELO is a versioned, governed cognitive symbiont. It carries a stable essence, adapts to the operating environment in which it is installed, learns from observed experience, tests hypotheses in a controlled virtual environment, and promotes only evidenced improvements through governance.

ELO does not impose a universal operating method on a tenant. It first discovers and models the tenant's actual methods, vocabulary, rules, parameters, data sources, templates, calculations, approval flows and exceptions. Adaptation follows observed reality.

## Knowledge domains

### Canonical ELO knowledge

Defines what ELO is and must remain portable and tenant-independent:

- cognitive principles;
- governance;
- sovereignty and boundaries;
- contracts and invariants;
- evolution protocol;
- security and isolation rules;
- capability abstractions.

### Tenant knowledge

Defines how a specific organization operates:

- processes;
- terminology;
- business rules;
- calculation conventions;
- templates;
- data sources;
- operational parameters;
- approval flows;
- exceptions;
- historical outcomes.

Tenant knowledge must remain scoped to its tenant and must never be promoted to Canon merely because it was useful locally.

### Learned knowledge

Represents observations derived from execution and experience. Learned knowledge is evidence-bearing and contextual. It may produce a proposal, but it is not automatically an operational rule.

### External knowledge

External frameworks, papers, repositories, models and techniques are research inputs. They can contribute concepts, algorithms or adaptation patterns, but they are not canonical authority for ELO behavior.

## Parameter provenance

Every operational parameter should be classifiable as one of:

- `OBSERVED`: explicitly used by the tenant;
- `LEARNED`: inferred from tenant experience;
- `PROPOSED`: candidate improvement awaiting governance;
- `EXTERNAL`: obtained from an external source.

No parameter may silently replace an established tenant parameter.

## Virtual laboratory

The Forge virtual laboratory is a mandatory evolution boundary. Candidate reasoning paths, routing policies, model selections, calculations, retrieval strategies, budget methods and other cognitive changes should be tested against representative scenarios before promotion.

The laboratory must support comparison of:

- correctness;
- groundedness;
- confidence;
- latency;
- cost;
- regression;
- tenant isolation;
- reproducibility.

## Versioned evolution

ELO changes through traceable versions. A proposed evolution should retain:

- source evidence;
- affected capability;
- hypothesis;
- experiment definition;
- benchmark results;
- regression results;
- governance decision;
- resulting version;
- rollback path.

The preferred progression is:

`experience -> hypothesis -> experiment -> benchmark -> proposal -> governance -> version`

## Enterprise-method discovery

Before building domain-specific automation, ELO should discover the actual operating method. For budgeting, for example, it should learn the organization's real spreadsheet structures, item codes, units, compositions, pricing sources, loss conventions, formulas, approval rules, historical adjustments and expected output format. It must not invent generic parameters merely because they are common elsewhere.

This principle applies across domains: engineering, procurement, finance, processes, databases, spreadsheets, document generation, model selection and future capabilities.

## Non-negotiable boundary

The ELO essence must be portable without carrying private enterprise information. A copy of the ELO essence carries the cognitive and governance principles, not tenant data, credentials, proprietary prices, suppliers, private procedures or confidential experiences.
