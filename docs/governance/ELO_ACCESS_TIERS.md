# ELO Access Tiers — Collaborator and Visitor\n\n## Status\n\nImplemented on the governed `feat/elo-operator-binding-runtime` branch; production activation is gated by merge and migration application.\n\n## Access model\n\n| Tier | Consultation | Lista-Mãe INSERT | Lista-Mãe UPDATE/DELETE | GitHub repository |\n|---|---:|---:|---:|---:|\n| `COLABORADOR` | Yes | Yes | No | No |\n| `VISITANTE` | Yes | No | No | No |\n\n### Collaborator\n\n`COLABORADOR` receives:\n- `PORTAL_READ`\n- `PCP_READ`\n- `LISTA_MAE_INSERT`\n\nThe collaborator may insert new Lista-Mãe records but has no UPDATE or DELETE policy.\nA collaborator does not receive a GitHub operator binding. Therefore the GitHub repository is not part of this access tier.\n\n### Visitor\n\n`VISITANTE` receives:\n- `PORTAL_READ`\n\nThe visitor can use authorized consultation surfaces but receives no Lista-Mãe write capability and no GitHub operator binding.\n\n## Database boundary\n\n`public.lista_mae` has RLS enabled.\n- SELECT requires `PCP_READ`.\n- INSERT requires `LISTA_MAE_INSERT`.\n- No UPDATE/DELETE policy is created for the collaborator tier.\n- Visitor access remains portal-level; it is not direct database access to Lista-Mãe.\n\nThe RLS helper resolves:\n\n`auth.uid() → elo_identity_registry → elo_identity_roles → elo_roles → elo_role_capabilities → elo_capabilities`\n\nNo user metadata is used as an authorization source.\n\n## Provisioning\n\nThis migration creates the role/capability definitions only. It does not automatically create or elevate any human identity.\n\nIndividual collaborator/visitor accounts must be provisioned through the canonical ELO identity/authorization path and receive only the intended role and scope.\n\n## Security invariant\n\n`Google authentication != GitHub repository access != ELO authorization capability`\n\nAuthentication identifies the person. ELO authorization determines what that identity may do.
